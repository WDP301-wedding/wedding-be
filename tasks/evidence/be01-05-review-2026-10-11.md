## Required finding

**P2 — Batch template eligibility checks before returning a print catalog page.**
`src/modules/venue-catalog/application/print-offering.service.ts:135–141` loops
over the page inside one interactive transaction and calls
`templates(tx).requireSelection(row)` sequentially for each offering. Each call
performs a template lock, a head query and a version query in
`src/modules/invitation-studio/infrastructure/template-selection.reader.ts`.
Even offerings sharing the same exact template repeat those three operations.
The transaction uses the client's default five-second deadline.

The API accepts `limit=50`. A disposable PostgreSQL reproduction created 50 valid
active offerings referencing one active/current template. The unmodified HTTP
route returned **200 with all 50 items** without injected delay. With **40 ms of
controlled delay before each of the three template queries**, the same valid
`GET /api/v1/catalog/print-offerings?limit=50` returned **500 INTERNAL_ERROR**
after **5,044 ms**, having started **105 template queries**. A preceding direct
service probe captured Prisma **P2028**, explicitly reporting the **5,000 ms**
transaction timeout. These are controlled latency results, not an assertion that
the current Railway database has that latency or that a deployed request failed.

Expose a bounded batch eligibility operation through Invitation's owner port,
deduplicate exact template references, and fetch/check heads and immutable versions
in a small number of queries. Retain active/current checks and the required lock
lifetime. Verify both repeated-template and distinct-template pages with controlled
query latency and template revision/archive races; increasing the timeout alone
leaves the sequential query amplification.
